# /next-fix — 次に直すシーンと、その直しどころを見つける

ユーザーの入力: `$ARGUMENTS`

入力があれば絞り込みの観点として使う（「色が気になる」「動きが騒がしいもの」など）。
空でよい。**対象のシーン名をユーザーに聞かない。選ぶのがこのスキルの仕事。**

このスキルが出すのは**改善カード 1 枚**で、実装はしない。Phase 4 で止めて引き渡す。

---

## このスキルの立ち位置

シーンは 23 本ある。勘で選ぶには多いので、**先に全体を見てから 1 本に絞る**。

| | 判断するのは | 何が起きるか |
| --- | --- | --- |
| `archive-scene`（外す） | **ユーザー**。スキルは候補を挙げない、評価もしない | タブから消える |
| `next-fix`（直す） | **Claude** が候補を挙げて順位を付け、ユーザーが選ぶ | 何も消えない |

**このスキルが出した候補を、そのままアーカイブの提案に流さない。**
`archive-scene` は「勝手に候補を選んだり『これはいまいちだと思います』と評価したりしない」と
決めてある。直す提案と外す提案は別物で、外すかどうかを決めるのはユーザーだけ。

---

## Phase 0 — 撮らないと決める

**棚卸しの段階で `npm run shot` を叩かない。** 23 本撮れば往復も文脈も潰れる
（PNG 1 枚がおよそ 1,000 トークン）。絵を見るのは候補を 1 本に絞ったあとの Phase 3 だけ。

このスキルは worktree の中から呼ばれることがある。**worktree のセッションでは、
`for` ループやコマンド置換を連ねた Bash は「worktree の外に出ないことを検証できない」として
拒否される。** 下のコマンドはすべて単純な 1 本になっているので、繋ぎ直さずそのまま叩くこと。

---

## Phase 1 — テキストだけで棚卸しする

3 つを順に叩く。**シーンファイルを `cat` で開かない。**

### 1. 手入れの回数（これが主軸の信号）

```bash
git log --pretty=format: --name-only -- src/scenes/ | sort | uniq -c | sort -n
```

`1` のものは**初版から一度も直されていない**。`_archive/` の行と、いま存在しない
ファイル名（過去に改名・削除されたもの）は読み飛ばす。`index.ts` も対象外。

タブの並びも手がかりになる。**タブは git がそのファイルを追加した時刻の新しい順**に出る
（`scripts/scene-order.mjs`）。つまり**タブの末尾に近いシーンほど古い**。
これは「追加された時刻」であって「最後に触った時刻」ではないので、上の回数と併せて見る。

### 2. 冒頭コメントと desc

```bash
grep -n "desc:\|気持ちよさの芯\|スコープ外" src/scenes/*.ts
```

`desc:` は 23 本すべてにあるが、`気持ちよさの芯:` と `スコープ外:` を持つのは 6 本だけ。
**これは書式が途中で導入されたためで、持っていないことは欠点ではない。**

### 3. これまで何が直されてきたか

```bash
git log --date=short --pretty=format:"%ad %s" -- src/scenes/ | head -30
```

件名は「&lt;シーン名&gt; の &lt;対象&gt; を &lt;どうした&gt;」で揃っている。**直近に出てくるシーンは
手が入ったばかり**なので候補から下げる。逆に、ここに一度も出てこない名前が狙い目。

---

## Phase 2 — 候補に順位を付ける

**1 つの手がかりだけで決めない。** 4 つを突き合わせて上位 3〜4 本を出し、
**順位の根拠を 1 行ずつ添える**（「コミット 1 本、09-06 から無変更」のように数字で書く）。

| # | 手がかり | 強い兆候 | 使える範囲 |
| --- | --- | --- | --- |
| ① | **手入れ履歴** | コミットが 1 本きりで、追加から日が経っている | 全 23 本。**主軸** |
| ② | スコープ外の自白 | 「近似している」「〜で代用」「〜に見立てている」と書いてある | 6 本のみ。**あれば最有力** |
| ③ | 気持ちよさの芯との突き合わせ | 芯が「〜する瞬間」なのに、その瞬間が絵として立っていなさそう | 7 本のみ |
| ④ | `desc` と実物の差 | 題材（ラバランプ・クラゲ・魚）が実際どう見えるかとのずれ | 全 23 本 |

②は作った本人が「ここは妥協した」と書き残した行なので、当たれば確度がいちばん高い。
ただし**持っているのは最近作られた 6 本に偏っている**（＝直す必要が薄い側）。
②だけで選ぶと、いちばん手が入っているシーンを選んでしまう。必ず①と併せて見る。

**仕様カードを持たない 16 本を「情報が無いから」と外さない。** 狙いが言語化されていない
というだけで、①と④で評価できる。むしろ放置されている可能性が高い側になる。

**直すのは 1 本だけ。** 2 本同時に提案しない。

---

## Phase 3 — 1 本に絞ってから、初めて撮る

ユーザーが選んだら（または上位 1 本で合意したら）、そこで初めて撮る。

```bash
npm run shot -- <camelCase>
```

目的は **Phase 2 で立てた仮説が、絵の上で本当に成り立つかを確かめること**。
**仮説が外れていたら候補を差し替える。** 撮る前に決め打ちで Phase 4 へ進まない。

PNG の扱い（自分で `Read` しない／`scene-critic` エージェントに講評させる手順）は
`.claude/skills/new-scene/SKILL.md` の Phase 6 が正本。見え方の定性チェック 6 項目は
`.claude/skills/new-scene/references/recipes.md` の「見え方のセルフチェック」が正本。
**どちらもここに写さない。** 2 か所に置くと必ず食い違う。

## Phase 4 — 改善カードにまとめて引き渡す

この形で出して**止まる**。実装はこのスキルの仕事ではない。

```
対象:            src/scenes/<camelCase>.ts（タブ #N）
選んだ理由:      Phase 2 のどの手がかりが効いたか。履歴の数字を添える
いまどう見えるか: Phase 3 で撮って分かったこと（1〜2 行）
何が足りないか:  「前はこうだった」を言い切る（1〜2 行）
直し方の案:      1〜3 行
規模の見立て:    造形の作り直し（300 行規模）/ 定数の振り直し（数行）のどちらか
動くスコープ外:  直したあと スコープ外: をどう書き換えるか
直す価値:        直しても救えないと思うならそう書く
見送るもの:      今回は触らないと決めたもの
```

要点は 3 つ。

- **`動くスコープ外` を必ず書く。** 改善とは「スコープ外の線を 1 段深いところへ動かすこと」で、
  それが書けないなら、それは改善ではなく作り直しになっている。スコープ外の行を持たないシーンなら、
  ここで新しく書き起こす（改善のついでに冒頭コメントが仕様カードの形に揃う）。
- **`直す価値` を必ず問う。** 履歴上、改善を 1 回受けてからそれでもアーカイブされたシーンが
  3 本ある。手を入れても救えないと思うなら正直に書く。**ただし外す判断まで踏み込まない。**
- **`規模の見立て` を外さない。** 過去の改善は「造形をまるごと作り直す 300〜500 行」と
  「定数 1〜2 行の振り直し」に二極化している。後者で足りるのに前者を提案しない。
  逆に、定数をいじって済ませられない破綻を定数の話にしない。

カードの並びは、そのまま改善コミットのメッセージに流せるようにしてある
（件名が「&lt;シーン名&gt; の &lt;対象&gt; を &lt;どうした&gt;」、本文 1 段落目が「前はこうだった → こう変えた」）。

---

## Phase 5 — 実装へ渡す

実装の約束（触ってよいのは自分のシーン 1 ファイルだけ、`typecheck` → `build` →
`smoke` → `shot`、`merge-scene` で取り込む）は `CLAUDE.md` と `new-scene` が正本。
**ここに写さない。** 伝えるのはブランチ名だけでよい。

- 既定は **`scene/<既存シーンの kebab 名>` を再利用**する（`merge-scene` がこれを前提にしている）
- 実装方式ごと入れ替える改善のときだけ、接尾辞を付けた別名にする
  （例: `scene/lava-lamp` に対して `scene/lava-lamp-shader`）

---

## 触らないもの

このスキルは**何も編集しない**。読むだけで、出力は改善カード 1 枚。

`src/scenes/*.ts` も `src/scenes/index.ts` も書き換えない。
「ついでに直しておきました」をしない。直すのは、カードをユーザーが承認したあとの別作業。
